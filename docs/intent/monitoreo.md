# Monitoreo administrativo

El monitor es una app separada del juego, con frontend estático propio en S3 y una Lambda de lectura. CloudFront protege página y archivos con Basic Auth: el usuario es `monitor` y la contraseña la configura el operador. Para consumo programático, el mismo `GET /api/metrics` acepta `x-api-key` por HTTPS, sin requerir Basic Auth o Cognito. Esa key autoriza únicamente el GET de la ruta exacta; si el header está presente, debe contener una key válida y no hay fallback a Basic Auth. Sin ese header se conserva el acceso Basic actual, incluido el challenge. La key no autoriza otras rutas o métodos. En cada solicitud aceptada se retiran `authorization` y `x-api-key` antes del origen; los orígenes S3 y Function URL siguen privados y no permiten acceso anónimo directo. La Lambda devuelve el mismo JSON de métricas y conserva cálculos, datos ausentes, frescura, errores y ausencia de caché actuales. El dashboard y su build no reciben la API key. Las cuentas de jugadores siguen ingresando mediante Cognito en el juego.

La Lambda del monitor usa Node.js 22 sobre x86_64, X-Ray `Active`, logs JSON y la capa pública fijada `arn:aws:lambda:us-east-1:615299751070:layer:AWSOpenTelemetryDistroJs:16` mediante `/opt/otel-instrument`. Es una configuración de trazas solamente (`OTEL_TRACES_EXPORTER=otlp`, `OTEL_METRICS_EXPORTER=none`, `OTEL_LOGS_EXPORTER=none`, `OTEL_AWS_APPLICATION_SIGNALS_ENABLED=false`); no hay collector ni pipeline de métricas nuevo. Las llamadas de Cognito y DynamoDB quedan en spans CLIENT creados por la propia Lambda porque los SDK siguen dentro del bundle. Cada invocación escribe objetos JSON consultables con `lambdaRequestId`, `trace_id` de 32 hexadecimales y el resultado; no se registran cuerpos privados, credenciales ni mensajes arbitrarios de dependencias.

El dashboard muestra el inventario actual de usuarios con `email_verified=true`, incluidas las cuentas deshabilitadas verificadas. Registrados no es un acumulado histórico de cuentas eliminadas. Nuevos cuenta la creación de esas cuentas dentro de ventanas móviles de 24, 72 y 168 horas, con un mismo corte UTC por consulta y ambos bordes incluidos. La lectura agota todas las páginas de Cognito y deduplica por `sub`. Cognito es eventualmente consistente: el corte temporal no promete un snapshot transaccional.

En cada actualización, la Lambda fija `asOf`, agota las páginas de Cognito y recorre secuencialmente la tabla existente con un `Scan` paginado y lectura fuerte por ítem. Filtra cabeceras `PK=USER#<sub>/SK=ATTEMPT#<id>`, llamadas `PK=ATTEMPT#<id>/SK=CALL#<seq>` y actividad `PK=USER#<sub>/SK=ACTIVITY`, y proyecta sólo `PK`, `SK`, `createdAt`, `score`, contadores de uso, `budget.rates` y `lastLoginAt`. No lee cuerpos privados, borradores, acciones, reservas ni acumulados del ledger. No se crean índices ni nuevas tablas; el monitor sigue siendo de sólo lectura. El Scan evalúa toda la tabla: la lectura y su duración crecen con el historial retenido, aunque el filtro y la proyección reduzcan los datos devueltos. `generatedAt` se fija al completar las lecturas. El corte temporal no es un snapshot transaccional de Cognito y DynamoDB ni entre páginas. Las comprobaciones publicadas deben leer el registro JSON de una invocación nueva y contrastar `lambdaRequestId` y `trace_id` con la misma traza en CloudWatch Omni/X-Ray, además de comprobar una invocación fría y otra caliente sin timeout u OOM.

Actividad significa iniciar sesión exitosamente en Cognito. Al cargar el editor, `GET /draft` toma `auth_time` del access token validado, después de comprobar la identidad y el email confirmado, y conserva la mayor fecha por `sub` en `USER#<sub>/ACTIVITY.lastLoginAt`, como ISO UTC. La actualización es condicional y atómica; no modifica el borrador. Renovar tokens, restaurar la sesión o recargar conserva la fecha original de autenticación. Se omiten fechas ausentes, inválidas o futuras respecto del reloj del servidor. El registro tiene una espera acotada y sus fallas se registran operativamente sin impedir la carga del borrador.

Última sesión muestra la mayor fecha válida registrada, o `N/A` si no hay una. Activos cuenta cada cuenta confirmada una sola vez si esa fecha cae en la ventana inclusiva de 24, 72 o 168 horas hasta `asOf`. Las cuentas sin fecha no aportan al conteo; una suma vacía devuelve cero. Una fecha anterior a siete días sigue visible en la tabla. Una fecha válida posterior al corte se muestra pero no cuenta en esas ventanas, porque puede provenir de una autenticación concurrente. El historial previo no se reconstruye: una sesión vigente anterior puede aportar su fecha original cuando vuelve a cargar el juego. Sólo se conocen las sesiones observadas por esa petición de la API; abandonar el flujo antes o una falla de registro puede dejar ese dato sin capturar hasta una carga posterior. No se usan intentos, creación de cuenta ni uso general de la app como reemplazo del login.

El costo de Bedrock se calcula por llamada con el uso observado y las tarifas guardadas en ese registro (`budget.rates`), sin consultar precios actuales ni usar reservas o `settledMicros` como reemplazo. Cada llamada calculable se redondea hacia arriba a microdólares antes de sumarse. Se incluyen llamadas con consumo aunque el intento haya fallado o se haya cancelado. Las llamadas con fecha, uso o tarifa insuficientes se omiten; no invalidan las demás. Una suma sin llamadas calculables devuelve cero.

Los costos usan `createdAt` de cada llamada en las ventanas móviles inclusivas de 24, 72 y 168 horas respecto de `asOf`; se excluyen fechas posteriores al corte. El total incluye las llamadas calculables de toda la tabla, aunque falte su cabecera o su propietario no figure en el inventario Cognito actual. Sólo se atribuyen a una fila las llamadas relacionadas con una cabecera de un usuario confirmado, por lo que el total puede superar la suma de las filas. Estos importes son cálculos de la aplicación a partir del uso y las tarifas guardadas; no son una conciliación de la factura AWS.

La tabla tiene diez columnas: usuario, registro, última sesión; intentos usados en 24 horas, 3 días y 7 días; costos de Bedrock en esos mismos períodos; y puntaje máximo. Todas se ordenan en ambas direcciones: números como números, fechas por instante y texto en español; `N/A` queda al final y los empates se resuelven de forma estable. Las fechas se presentan en horario de Argentina.

Cada cabecera `ATTEMPT#` cuenta un intento admitido, incluso si luego se cancela o termina en error. Rechazos, duplicados y reproducciones no crean otro intento. Los registros internos de REQUEST, CALL, STATE y ACTION tampoco cuentan por separado. Los conteos de intentos usan el mismo corte UTC de la consulta, incluyen ambos bordes de 24, 72 y 168 horas y excluyen fechas posteriores al corte. El puntaje máximo toma el mayor `score` numérico finito guardado entre todas las cabeceras del usuario, sin limitarlo a siete días, filtrar por resultado/nivel/versión ni recalcular la fórmula del juego. Cero y valores negativos son válidos; un score nulo, ausente o no numérico se ignora.

Un usuario sin cabeceras tiene cero intentos en cada período y `N/A` como puntaje máximo. Una fecha de cabecera `createdAt` ausente o ilegible hace que sus tres conteos de intentos sean `N/A`; no impide devolver un puntaje conocido. La falta de un score válido hace que sólo el máximo sea `N/A`. Estos casos son distintos de cero. Un error de IAM, servicio, paginación inconclusa o cursor repetido falla la solicitud completa con HTTP 503; no devuelve el inventario ni las métricas parcialmente leídas.

Entrar, recargar o pulsar **Actualizar** consulta datos nuevos. Durante carga el botón queda deshabilitado y no se muestran resultados anteriores. Ante error se informa la falla y se permite reintentar manualmente. Un error operativo o inventario incompleto no se convierte en una respuesta parcial ni en `N/A`. Una consulta completa sin usuarios produce cero registrados/nuevos y una tabla vacía; el total de costos sigue proviniendo del Scan y no depende de que existan filas visibles.

No hay polling, persistencia de resultados en el navegador ni caché de métricas. Los archivos con hash pueden usar caché HTTP normal, después de validar el acceso en cada solicitud. El navegador administra las credenciales Basic; la app no almacena contraseñas ni incorpora credenciales AWS. El rol runtime de la Lambda puede usar `cognito-idp:ListUsers` en el User Pool existente, `dynamodb:Scan` sobre el ARN exacto de la tabla `prompt-runner-game-drafts`, publicar sus segmentos y telemetría X-Ray, y escribir en sus propios logs operativos. No tiene `Query`, escrituras u otras lecturas de DynamoDB, acceso a índices, cuerpos privados ni permisos de Bedrock.
