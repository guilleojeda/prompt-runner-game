# Monitoreo administrativo

El monitor es una app separada del juego, con frontend estático propio en S3 y una Lambda de lectura. Su distribución CloudFront exige Basic Auth con el usuario `monitor` y la contraseña configurada por el operador. La protección cubre página, archivos y datos; los orígenes S3 y Function URL no permiten acceso anónimo directo. Las cuentas de jugadores siguen ingresando mediante Cognito en el juego.

El dashboard muestra el inventario actual de usuarios con `email_verified=true`, incluidas las cuentas deshabilitadas verificadas. Registrados no es un acumulado histórico de cuentas eliminadas. Nuevos cuenta la creación de esas cuentas dentro de ventanas móviles de 24, 72 y 168 horas, con un mismo corte UTC por consulta y ambos bordes incluidos. La lectura agota todas las páginas de Cognito y deduplica por `sub`. Cognito es eventualmente consistente: el corte temporal no promete un snapshot transaccional.

Por cada `sub` verificado, la Lambda consulta con lectura fuerte todas las páginas de DynamoDB para `PK=USER#<sub>` y prefijo de sort key `ATTEMPT#`. Sólo lee las claves, `createdAt` y `score`; no escanea la tabla ni lee cuerpos privados. Los usuarios no verificados no generan filas ni consultas. `asOf` se fija antes de consultar las fuentes y `generatedAt` después de completar las lecturas. Es un corte temporal común, no un snapshot transaccional de Cognito y DynamoDB ni entre páginas.

Actividad significa iniciar sesión exitosamente. Las fuentes actuales no permiten atribuir esos ingresos a cada cuenta ni conocer el gasto real de Bedrock por aplicación/usuario en las ventanas solicitadas. Activos, última sesión y costos conservan sus campos y muestran el string literal `N/A`. No se reemplaza gasto por reservas o estimaciones, ni desconocidos por cero.

La tabla tiene diez columnas: usuario, registro, última sesión; intentos usados en 24 horas, 3 días y 7 días; costos de Bedrock en esos mismos períodos; y puntaje máximo. Todas se ordenan en ambas direcciones: números como números, fechas por instante y texto en español; `N/A` queda al final y los empates se resuelven de forma estable. Las fechas se presentan en horario de Argentina.

Cada cabecera `ATTEMPT#` cuenta un intento admitido, incluso si luego se cancela o termina en error. Rechazos, duplicados y reproducciones no crean otro intento. Los registros internos de REQUEST, CALL, STATE y ACTION tampoco cuentan por separado. Las ventanas usan el mismo corte UTC de la consulta, incluyen ambos bordes de 24, 72 y 168 horas y excluyen fechas posteriores al corte. El puntaje máximo toma el mayor `score` numérico finito guardado entre todas las cabeceras del usuario, sin limitarlo a siete días, filtrar por resultado/nivel/versión ni recalcular la fórmula del juego. Cero y valores negativos son válidos; un score nulo, ausente o no numérico se ignora.

Un usuario sin cabeceras tiene cero intentos en cada período y `N/A` como puntaje máximo. Una fecha `createdAt` ausente o ilegible hace que sus tres conteos de intentos sean `N/A`; no impide devolver un puntaje conocido. La falta de un score válido hace que sólo el máximo sea `N/A`. Estos casos son distintos de cero. Un error de IAM, servicio, paginación inconclusa o cursor repetido falla la solicitud completa con HTTP 503; no devuelve el inventario ni los conteos parcialmente leídos.

Entrar, recargar o pulsar **Actualizar** consulta datos nuevos. Durante carga el botón queda deshabilitado y no se muestran resultados anteriores. Ante error se informa la falla y se permite reintentar manualmente. Un error operativo o inventario incompleto no se convierte en una respuesta parcial ni en `N/A`. Una consulta completa sin usuarios produce cero registrados/nuevos y una tabla vacía.

No hay polling, persistencia de resultados en el navegador ni caché de métricas. Los archivos con hash pueden usar caché HTTP normal, después de validar el acceso en cada solicitud. El navegador administra las credenciales Basic; la app no almacena contraseñas ni incorpora credenciales AWS. El rol runtime de la Lambda puede usar `cognito-idp:ListUsers` en el User Pool existente y `dynamodb:Query` en la tabla existente `prompt-runner-game-drafts`, además de escribir sus logs operativos propios. No tiene `Scan`, lecturas o escrituras adicionales de DynamoDB, acceso a índices, cuerpos privados ni permisos de Bedrock.

La configuración y entrega están en [acceso y entrega](../architecture/acceso-y-entrega.md#monitor-administrativo).
